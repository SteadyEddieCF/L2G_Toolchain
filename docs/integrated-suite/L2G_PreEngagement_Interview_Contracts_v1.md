# L2G Integrated Suite v0.5.0 — Pre-Engagement and Interview Field-Level Contracts

## Status

Proposed design contract for issue #133. This document authorizes no implementation until reviewed and merged with ADR-0010, the Interview Mode UX record, threat model, and acceptance matrix.

## Shared rules

All IDs are opaque, immutable, lowercase-prefixed strings generated by the integrated application. Timestamps are RFC 3339 UTC. Records contain `created_at`, `created_by_profile`, `updated_at`, `revision`, `lifecycle`, `visibility`, and optional `supersedes_id` unless a narrower rule applies.

All cross-domain references use `{domain, record_type, record_id, revision?}`. Missing or invalid references are rejected before mutation. Imported identifiers are stored only in provenance and never reused as integrated authority IDs.

Every import, batch apply, session transition, candidate publication, migration, and consequential bulk action is atomic, command-based, recorded in history, and checkpointed where identified below.

## Archive entries

- `domains/pre-engagement.json` — `l2g_pre_engagement_v1`, version `1.0`.
- `domains/interview-sessions.json` — `l2g_interview_sessions_v1`, version `1.0`.

Each domain document contains `kind`, `version`, `domain_revision`, `records`, `receipts`, and `projection_metadata`. Unknown top-level fields are rejected in governed imports.

# 1. Pre-Engagement contracts

## 1.1 Intake request

`intake_request_id` prefix: `intake_`.

Required fields:

- `title`;
- `purpose`;
- `request_type`: `questionnaire`, `inventory`, `document-request`, `meeting-preparation`, `confirmation`, or `other`;
- `owner_ref` to an Engagement participant when known;
- `due_at` or explicit `no_due_date_reason`;
- `lifecycle`;
- `operational_state`;
- `review_state`;
- `visibility`;
- `requested_definition_refs`;
- `source_refs`;
- `rationale`.

A request does not contain answers. Closing or cancelling a request does not delete assignments, submissions, receipts, reviews, exceptions, or candidates.

## 1.2 Assignment

`assignment_id` prefix: `assign_`.

An assignment binds one request to one or more intended respondent references and one frozen definition snapshot. Required fields include:

- `intake_request_id`;
- `respondent_refs`;
- `definition_snapshot_id`;
- `issued_at`;
- `due_at` or no-due-date reason;
- `operational_state`;
- `delivery_method`: `local-record`, `external-manual`, or `imported`;
- `instructions`;
- `reminder_records`.

v0.5 reminders are local work records only. No email or external notification is sent.

## 1.3 Definition and version

`definition_id` prefix: `definition_`; `definition_version_id` prefix: `defver_`.

Definition kinds are `questionnaire` and `inventory`. A version contains:

- stable definition reference;
- semantic version or monotonically increasing integer;
- title and purpose;
- ordered item versions;
- helper text;
- completion rules;
- provenance;
- lifecycle;
- visibility.

Published/issued versions are immutable. Editing creates a new version.

## 1.4 Definition item

`definition_item_id` prefix: `defitem_`; version prefix: `itemver_`.

Required fields:

- `prompt`;
- `item_type`: `short-text`, `long-text`, `single-select`, `multi-select`, `boolean`, `date`, `number`, `person-reference`, `organization-reference`, `system-reference`, `source-reference`, or `structured-row`;
- `required`;
- `answer_constraints`;
- `helper_text`;
- `applicability_note`;
- `source_refs`;
- `visibility`.

Answer constraints are declarative and bounded. No executable expressions or arbitrary HTML are permitted.

## 1.5 Submission and answer

`submission_id` prefix: `submission_`; `answer_id` prefix: `answer_`.

A submission references one assignment and exact definition snapshot. It contains respondent identity as asserted or Engagement-linked, started/completed timestamps, receipt state, and answer records.

Each answer includes:

- item-version reference;
- typed answer value;
- `answer_origin`: `participant-provided`, `advisor-entered-for-participant`, `imported`, or `unknown`;
- optional respondent attribution;
- source/provenance references;
- confirmation state;
- visibility;
- review state.

Source-derived content may never use `participant-provided` unless an explicit confirmation event establishes that status.

## 1.6 Receipt, review, and exception

`receipt_id` prefix: `receipt_`; `pre_review_id` prefix: `prereview_`; `exception_id` prefix: `prex_`.

A receipt records the arrival or import of a submission, package identity/hash where applicable, parser/adapter version, warnings, and disposition. A review records accepted, changes-requested, rejected, or retained-unresolved decisions with rationale. Exceptions identify missing, conflicting, malformed, overdue, incomplete, or ambiguous content without creating assessment conclusions.

## 1.7 Pre-Engagement candidate

`pre_candidate_id` prefix: `precand_`.

Fields:

- source request/submission/answer/review references;
- target domain and target type;
- proposed operation;
- bounded proposed fields;
- rationale;
- provenance;
- visibility;
- workflow state;
- target-owned candidate reference when published;
- supersession links.

# 2. Interview contracts

## 2.1 Question bank and version

`question_id` prefix: `question_`; `question_version_id` prefix: `qver_`.

Required fields:

- `prompt`;
- `short_label`;
- `origin`: `scripted`, `advisor-created`, `source-derived`, `questionnaire-derived`, `suggested-follow-up`, `carryover`, or `imported`;
- `rationale`;
- `expected_participant_refs`;
- `applicability_note`;
- `source_refs`;
- `visibility`;
- `lifecycle`.

Published question versions are immutable. Suggested questions remain candidates until included in a plan by an advisor command.

## 2.2 Session

`session_id` prefix: `session_`.

Required fields:

- `title`;
- `purpose`;
- `session_type`: `discovery`, `scope`, `practice`, `evidence`, `ssp`, `follow-up`, or `other`;
- facilitator reference;
- planned attendee references;
- scheduled start/end or explicit unscheduled reason;
- actual start/end when applicable;
- lifecycle;
- active plan snapshot reference;
- current agenda position;
- pause/resume metadata;
- completion-review state;
- visibility.

Actual attendance uses an immutable attendance snapshot captured during or after the session; it does not alter Engagement participant authority.

## 2.3 Session plan snapshot

`session_plan_id` prefix: `plan_`; `session_plan_item_id` prefix: `planitem_`.

A plan snapshot contains ordered items. Each item records:

- question-version reference;
- session-specific displayed prompt;
- inclusion state;
- order;
- rationale;
- expected participants;
- applicability note;
- source references;
- visibility;
- estimated duration;
- carryover origin where applicable.

A `ready` or started session always references a frozen snapshot. Subsequent plan edits create a new snapshot and explicit adoption event.

## 2.4 Response and note record

`session_record_id` prefix: `srec_`.

Required fields:

- session and plan-item references;
- `record_kind` from ADR-0010;
- content;
- attribution references where applicable;
- captured timestamp;
- source/provenance references;
- confirmation state;
- visibility;
- review state;
- conflict group reference where applicable;
- supersession links.

Content is plain text. Formatting is represented by bounded safe structure, not arbitrary HTML.

## 2.5 Confirmation event

`confirmation_id` prefix: `confirm_`.

A confirmation event records:

- exact session-record ID and revision;
- confirmer reference or asserted name/organization;
- method;
- timestamp;
- optional qualification;
- facilitator reference;
- provenance.

Confirmation does not imply acceptance by another domain.

## 2.6 Follow-up and parking-lot item

`followup_id` prefix: `followup_`; `parking_id` prefix: `parking_`.

Follow-ups contain owner reference, due date or no-date reason, operational state, source session-record references, and optional proposed target. Parking-lot items contain topic, defer rationale, intended revisit context, and lifecycle. Neither automatically creates a Reviews & Actions record until that target domain is implemented and explicitly accepts a candidate.

## 2.7 Facilitator summary

`summary_id` prefix: `summary_`.

Required fields:

- title;
- bounded summary text;
- cited session-record references;
- author profile;
- visibility;
- review state;
- client-approval metadata when `approved-client-summary`;
- supersession links.

A summary may not cite itself, cite hidden records in a Client projection, or silently replace raw records.

## 2.8 Interview candidate

`interview_candidate_id` prefix: `intcand_`.

The structure mirrors Pre-Engagement candidates and adds session, plan-item, statement/observation/summary, confirmation, and conflict references.

# 3. Import adapter contract

Every supported import produces a preview object containing:

- recognized kind/version;
- package SHA-256 and byte size;
- adapter and registry version;
- candidate counts by record class;
- source/provenance coverage;
- warnings, errors, ambiguous references, unsupported records, and excluded records;
- proposed stable integrated IDs generated only for preview and committed unchanged on apply;
- estimated post-apply domain counts and serialized size;
- exact mutation summary.

Apply is atomic. Rejected, cancelled, malformed, oversized, tampered, ambiguous, or unsupported input creates no governed records. A reviewed valid subset may be applied only when every excluded row is visible and the receipt records the exact subset.

# 4. Projection contract

Every workspace projection includes:

- source domain kind/version/revision;
- active profile;
- generated timestamp;
- visible record IDs and immutable summaries;
- factual next-work items;
- no direct mutable authority objects.

Client projections are generated from explicit visibility and approval fields before counts, indexing, sorting, snippets, inspector relationships, accessibility labels, or live-region text are built.

# 5. History and reversibility

Commands must produce human-readable Undo/Redo descriptions. Undo restores prior governed state but never deletes audit events. Reversal of a published or accepted candidate creates an explicit withdrawal, return, supersession, or reversal event; it does not erase the original transition.

Named checkpoints are mandatory before:

- v0.4-to-v0.5 migration;
- batch import apply;
- session start;
- pause;
- post-session completion;
- batch candidate publication;
- destructive supersession affecting dependent records.

# 6. Validation invariants

- IDs are unique within and across expected prefixes.
- references resolve to permitted record types.
- immutable snapshots cannot be edited in place.
- plan order is deterministic and contiguous.
- a session cannot start without a valid ready plan.
- a paused session has a successful checkpoint reference.
- summaries cite existing visible source records.
- Client projections contain no advisor-only content or metadata.
- candidate publication does not mutate target governed content directly.
- imports do not partially mutate on error.
- migration creates empty domains and no inferred content.
- no record field encodes readiness, compliance, certification, evidence sufficiency, scoring, risk, implementation, or Met/Not Met as an automatic conclusion.
